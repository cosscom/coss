---
title: Embedding
description: Coss.com's pages in your app, or your own UI, without your API key in a browser.
---

Your API key stays on your server. For a browser, your server creates a **session**: short-lived, for one
thing, with its token in the URL's fragment, which never reaches a server.

| Session | Lets the browser | Lasts |
|---|---|---|
| `createForHost` | Set one host's hours, connect their calendars, and manage their bookings: approve, decline, reschedule, cancel, mark a no-show | An hour by default, up to a day |
| `createForBooker` | Book one event type | 30 minutes by default, up to a day |
| `createForBooking` | Reschedule or cancel one booking | Until a day after it ends. Stops when it's cancelled |

In live environments, `createForHost` needs <PlansWith feature="schedulingHostPortal" />. On other plans, connect
a host's calendars and set their hours through the API. Live pages show "Scheduling by coss.com" below them, except on
<PlansWith feature="schedulingWhiteLabel" />.

```ts twoslash
import { Coss } from "coss";
const coss = new Coss();
const eventTypeId = "evtype_01kd2m9a0b1c2d3e4f5g6h7j8m";
// ---cut---
// On your server:
const { data: session } = await coss.scheduling.sessions.createForBooker({
  event_type: eventTypeId,
  // Someone you've signed in: the browser can't book as anyone else.
  attendee: { uid: "patient_77", name: "Sam Lee", email: "sam@example.com", time_zone: "UTC" },
});
// Pass session?.url to the browser.
```

To send them to a particular kind of host, add [`attributes`](/docs/scheduling/routing).

Open the `url` on its own, or embed it with `coss/scheduling`:

```ts
import { mountBooker, mountHostPortal } from "coss/scheduling";

mountBooker({
  url: session.url,
  container: document.getElementById("booking"),
  onEvent: (event) => {
    if (event.type === "booked") showThanks(event.booking_id);
  },
});

mountHostPortal({
  url: hostSession.url,
  container: document.getElementById("availability"),
});
```

The page's origin must be in your settings' `allowed_origins`:

```ts twoslash
import { Coss } from "coss";
const coss = new Coss();
// ---cut---
await coss.scheduling.settings.update({
  allowed_origins: ["https://app.example.com"],
  brand_name: "Acme Health",
});
```

Events carry ids and statuses only. The pages tell your app `ready`, `booked`, `rescheduled`, `cancelled`,
`availability_saved`, `calendar_connected` and `error`.

## Your own UI

A session's `token` also works directly from a browser, against the client API at
`/scheduling/client/*`, with `Authorization: Bearer <token>`. It's how coss.com's own pages work, so
nothing they do is out of your reach. Calls are only accepted from your `allowed_origins`, and a session
reaches only its own scope: an attendee sees times, never who else could take them.

A booking made this way says whether the attendee will be emailed about it (`attendee_emailed`), so your page
only promises a confirmation when one is coming. It can choose among the event type's `locations` by `type`, but
not supply its own link or address, only a phone number where the event type leaves that open.

Booker sessions have `GET /session`, `GET /slots` and `POST /bookings`. Manage sessions have
`GET /booking`, `GET /booking/slots`, `POST /booking/reschedule` and `POST /booking/cancel`. Host sessions
have `/host/schedules`, `/host/calendar_connections`, `/host/calendars/{id}`, `/host/locations` and `/host/bookings`
(with `?when=past`, those that started in the last 30 days), and for one of their bookings
`GET /host/bookings/{id}/slots` and `POST /host/bookings/{id}/approve`, `/decline`, `/cancel`, `/reschedule` and
`/no_show`. A host isn't held to the cutoffs attendees are, and can't move a booking to another host.
