## Organizations and projects

Everything in coss.com belongs to an **organization**. Members are owners, admins or members.
An organization has any number of **projects**, and each project has two **environments**:

| Environment   | Mode      | Key prefix   | Sends email                                      |
| ------------- | --------- | ------------ | ------------------------------------------------ |
| `production`  | `live`    | `coss_live_` | Yes, from your organization's verified domains   |
| `development` | `sandbox` | `coss_test_` | No. Emails are recorded with `sandbox: true`     |

## API keys

An API key belongs to exactly one environment, and everything it creates or reads lives in that
environment. A key can only read emails sent from its own environment.

### Permissions

When you create a key in the dashboard, you choose what it can do:

| Access             | Can                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------ |
| **Full access**    | Everything, including the permissions of products coss.com adds later                |
| **Sending access** | Only `email:send`: send, schedule and cancel emails through the API, the SDK or SMTP |
| **Read only**      | Every `read` permission below                                                        |
| **Custom**         | The permissions you check                                                            |

Keys with sending access, read-only access or custom permissions are **restricted**. A restricted key
keeps exactly the permissions it was created with: it never gains new ones, even when coss.com adds
products. Give each server or job the narrowest key that does its work: an application that only
sends email needs only sending access.

A request the key isn't allowed to make fails with `403` `permission_error`
(`insufficient_permissions`), and the message names the permission it needed. Any key can read
its own environment and access with `GET /v1/environment`
(`coss.environment.get()`: `api_key.access` and `api_key.permissions`) and revoke itself.
To change what a key can do, create a new key and revoke the old one.

Keys are secrets. Call coss.com from your server, never from a browser: the SDK refuses to run where a
`document` global exists unless you opt in with `dangerouslyAllowBrowser`.

Creating a live key requires a verified email address on your account.

## Sandbox behaviour

Sandbox keys accept any `from` address and never deliver anything. Delivery events are simulated
the way the Amazon SES mailbox simulator behaves, so you can test failure handling:

| Recipient                                  | Simulated events                                  | Recipient status |
| ------------------------------------------ | ------------------------------------------------- | ---------------- |
| any address outside `simulator.amazonses.com` | `email.delivered`                              | `delivered`      |
| `bounce@simulator.amazonses.com`           | `email.bounced` (permanent)                       | `bounced`        |
| `complaint@simulator.amazonses.com`        | `email.delivered`, then `email.complained`        | `complained`     |
| `suppressionlist@simulator.amazonses.com`  | `email.bounced` (on the suppression list)         | `suppressed`     |

Every sandbox email also gets `email.sent`.

Sandbox [SMS](/docs/sms) is simulated too: any `from` number works, and the
[SMS simulator's numbers](/docs/sms/testing) produce each delivery outcome.
